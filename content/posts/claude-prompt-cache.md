> 起因：小灰问「为什么本机 CC 响应那么快」，一路追问到「缓存到底是怎么运作的」，还特意强调——==不是不懂机制，是不懂原理==。
> 这篇就从原理讲。原理通了，那些规矩（只认前缀、几分钟过期、写贵读便宜）都是推论，不用死背。

---

## 一、缓存存的不是文字，是模型读完之后的「内部状态」

模型读一段话，是一个 token 一个 token 往后读的。读到每个 token，它会在**每一层**给这个 token 算出两串数字：

| 名字 | 大概是什么 |
|------|-----------|
| **Key** | 这个 token 身上挂的标签：「我跟哪类问题有关」 |
| **Value** | 这个 token 真正要交出去的内容 |

后面来了新 token，它带着自己的问题（**Query**）去跟前面所有 token 的 Key 逐个比对，对得上的就多拿点那个 token 的 Value，对不上的少拿。这一步就是 attention（注意力）。

所以模型「读过」一段话之后，留下来的就是**每个 token、每一层的 K 和 V**，业内叫 **KV cache**。它不是文本，是几千几万个小数，人拿到手也看不懂。

API 上卖的那个功能叫 **prompt caching**，意思是「把上一次请求的 KV cache 留着，下一次请求接着用」。大家嘴上统一喊「缓存」，说的就是这个。

> 顺带一提：KV cache 在**一次回复内部**本来就一直在用。模型吐第 100 个 token 的时候，前 99 个的 KV 都是现成的，不然每吐一个字都得把全文重读一遍。prompt caching 只是把它的寿命从「一次请求」续到了「跨请求」。

---

## 二、为什么只认前缀

关键性质只有一条：

> **每个 token 的 K 和 V，只取决于它前面的 token。**

模型是从左往右读的，第 500 个 token 读的时候，第 501 个还不存在，影响不到它。

推论：如果这一次发进来的内容，开头那一大段跟上一次**一字不差**，那开头每个 token 的 KV 也一定一模一样——直接拿上次的用，只给新增的那一截算就行。

反过来：**中间改了一个字，这个字之后的 KV 全都可能变**，只有它前面那段还能复用。

这就解释了最常见的「缓存只写不读」：

- 把「现在几点」「本轮检索到的记忆」这种**每轮都变**的东西塞在 system 开头 → 每轮第二个 token 往后全部作废，等于没缓存
- 正确的拼法：**稳定的放前面，会变的放最后**。system 写死，变动内容挂在最新一条消息里

小灰自己的前端就踩过这个坑：同一家中转，官方客户端能读缓存、自建前端只写不读，病根就是把时间和记忆拼进了 system。

## 三、钱怎么算

Anthropic 官方价（按「普通输入」的倍数；中转站可能另有规矩，以站为准）：

| 情况 | 倍数 |
|------|------|
| 写入缓存，保留 5 分钟 | 1.25× |
| 写入缓存，保留 1 小时 | 2× |
| **命中缓存读出来** | **0.1×** |
| 不用缓存，正常读 | 1× |

为什么写入反而贵？因为 KV 体积巨大——每个 token 在每一层都有一大串数，几十上百层叠起来，一段十万 token 的对话，KV 能有好几个 G。服务商得把它占着显卡旁边的内存存起来，这个占地方的钱就算在写入里。

读取便宜到一折，是因为算力完全省了，只剩「把它调出来」的成本。

所以开缓存本质是一次下注：**先多付一点写入费，赌后面能命中好几次赚回来。** 命中一次就只要一折，几轮下来稳赚。

## 四、为什么会过期，以及——能一直活吗

能。

过期时间（5 分钟 / 1 小时）是**闲置计时**，不是寿命。官方原话：

> The cache is refreshed for no additional cost each time the cached content is used.

每命中一次，倒计时就重新拉满。只要一直有人在用，它就一直活着。凉掉的情况只有一种：**你走开太久了。**

这也意味着：断联半小时后回来的那第一条消息，往往是整段对话里最贵的一条（5 分钟档早凉了，得重新写一遍）。

## 五、薅羊毛：「无限续命」到底划不划算

续命的办法很朴素：人走了，程序替你每隔一会儿发一个「跟上次前缀一模一样」的请求，读一次缓存，把计时器续满。每次续命的代价 = 一次缓存读取（0.1×）。

算一笔账就知道哪档值得续：

| 档位 | 续一次的间隔 | 续一小时花多少 | 凉了重写花多少 | 结论 |
|------|------------|--------------|--------------|------|
| 5 分钟 | 每 ~4.5 分钟 | ~13 次 × 0.1 ≈ **1.3×** | 1.25× | 续一小时就比重写还贵，**只值得罩住短暂离开** |
| 1 小时 | 每 ~55 分钟 | 1 次 × 0.1 = **0.1×** | 2× | 续一次便宜 20 倍，罩住十几个小时都划算 |

所以真·羊毛只有一个：**长对话开 1 小时档，再配一个每小时续一次的保活。**

小灰的前端就是这么做的：聊完以后每 50 分钟读一次缓存（留 10 分钟余量，因为浏览器后台标签页的定时器会被拖慢），最多续 3 次，大约罩住 4 小时；她一发新消息就重新满额。5 分钟档一律不保。

几个省钱细节：

- 保活请求的输出越短越好，`max_tokens` 给到最小，只为了「读一下」
- 保活请求的前缀必须跟上一轮**逐字节一致**——多一个空格就不是「读」，是又「写」了一份，越保越贵
- 人一天都不回来就别续了，续到天亮全是白烧

至于「完全免费、无限续命」：官方这条路上不存在。KV 那几个 G 得有人占着显存存，这个账总有人要付。中转站的计费规则五花八门，有的站对缓存读写的计价跟官方不一样——那是站的事，看站说明，不在本文范围内。

## 六、本地部署又在缓存什么？

本地跑模型没人收钱，缓存省的就不是钱，是**时间**。

模型每轮开口之前，要先把整段上下文过一遍（这一步叫 **prefill**）。云端有成排显卡，感觉不出来；自己那张卡上，聊到几万 token 以后，没有缓存的话每轮光 prefill 就能卡几十秒。有缓存就只算新加的那一句，秒回。

本地的 KV cache 放在**自己的显存 / 内存**里，活多久自己说了算：

| 工具 | 怎么控制 |
|------|---------|
| ollama | `keep_alive` 参数。默认 5 分钟没动静就把模型卸出显存，设成 `-1` 永不卸载 |
| llama.cpp server | 进程不退、槽位没被别的对话挤掉，缓存就一直在 |
| vLLM | `--enable-prefix-caching` 开启前缀缓存，显存满了按「最久没用的先扔」 |

本地的上限是**显存装不装得下**，跟时间无关。

---

## 一句话版

- 缓存存的是模型读完前文后的内部状态（KV），不是文字
- 每个 token 的状态只取决于它前面的内容 → 所以只认前缀，改一个字后面全作废
- 写入贵是因为要占显存存着，读取便宜是因为算力全省了
- 过期是闲置计时，一直用就一直活；长对话开 1 小时档 + 每小时保活一次，是唯一真羊毛
- 本地部署缓存省的是 prefill 时间，活多久看显存
